# 退役构建机镜像层复用配对（layer-matcher）

CI 值班员工具：构建机退役后，找出待重跑任务能从哪些**在役构建机**复用镜像层。
上传两份 CSV，系统按"层摘要"做等值连接，把相同摘要在两表中的**所有行对**列出，
每对只出现一次，产出 `任务号, 来源构建机, 层摘要` 清单 CSV。

## 需求对照

| 要求 | 实现 |
| --- | --- |
| Flask 网页上传两份 CSV | `app/app.py` + `app/templates/`，支持中文/英文列名别名 |
| 相同摘要所有行对、每对一次 | 分桶 + 分块嵌套循环等值连接，输出前不做去重、不丢行（自测校验唯一性） |
| 内存最多暂存 256 条输入记录、256 条结果 | 每侧块大小 128（合计 256）；结果满 256 立即刷盘；`BoundedMemoryGuard` 运行时强制，越界即抛异常；自测断言整次运行峰值 |
| 只统计重启后仍能保留的配对 | 配对数始终由磁盘上已确认的结果批次重数（`count_pairs_on_disk`），不依赖内存 |
| 写盘中断可续跑、已确认批次不重算 | 工作单元 = (桶, 任务块, 机器块)；单元结果原子写盘后才推进 `state.json`（原子 rename + fsync）；续跑按状态跳过已确认单元，重算前清理本单元残留 |
| 全部完成后才开放 CSV 下载 | 仅当最终 `pairs.csv` 生成后下载路由返回 200，否则 409 |
| 清单列出任务号、来源构建机、层摘要 | 最终 CSV 表头即这三列 |
| Docker Compose 启动 | `docker compose up --build`，命名卷 `layer_matcher_data` 持久化断点状态 |

### 重启恢复与并发调度（本轮新增）

| 要求 | 实现 |
| --- | --- |
| 恢复扫描移到后台，值班员不用等目录扫完 | 首次请求只"踢"一下后台线程（`_start_recovery_once`），首页/作业页/上传立即返回；扫描失败下次请求会重试 |
| 上传新作业、凭原链接查看旧作业不受扫描影响 | 页面与上传都不持恢复锁、不等扫描；作业页直接读该作业目录 |
| 同一实例最多同时跑两份配对 | `MAX_CONCURRENT_JOBS=2`；调度器按执行位补位 |
| 重启前接单的作业最多占一个名额，空位都给新作业 | 新/旧作业分两条队列；`MAX_RECOVERED_RUNNING=1`，另一个执行位优先给新上传作业 |
| 等候作业不占执行线程 | 等候只占内存队列条目；线程仅在拿到执行位时创建（自测断言排队作业不在 `_threads` 中） |
| 上传文件与可恢复状态落盘后才确认接单 | 流式写入点开头暂存目录并 `fsync`，`state.json`（`phase=queued`）落盘、目录 `fsync` 后原子改名为正式作业目录，再入队 |
| 写入失败就报错，半成品不得进入队列 | 任一写入/校验失败返回 500/400、删除暂存目录、不入队；重启时清理上次崩溃留下的 `.incoming-*` 暂存目录 |
| 网页区分等候与运行 | 首页徽标"运行中 / 等候执行"，作业页"已接单，等候执行"；状态 JSON 带 `queue_status` |
| 扫描、页面访问、接单交错时同一作业最多一个执行者 | `_jobs_lock` 下统一登记 `_tracked` / `_uploading`；扫描、上传、完工都在同一把锁内去重，自测用 3 个并发扫描 + 上传 + 页面访问验证每作业只执行一次 |
| 再次重启后，已接单但未开跑的作业也入队 | `phase=queued` 属于可恢复阶段；引擎开跑时原子推进为 `partitioning` |
| 已开跑的从确认断点接续 | 沿用引擎的单元级检查点；队列状态与引擎状态同文件，重启只读盘 |

## 算法与内存边界（`app/join_engine.py`）

1. **分桶（partition）**：流式读两份 CSV，用跨进程稳定的 FNV-1a 哈希把记录路由到
   64 个磁盘分桶文件；该阶段内存只持有当前 1 条记录。
2. **分块嵌套循环连接（block nested-loop join）**：逐桶处理，每侧每次最多载入
   128 条（两侧合计 ≤ 256 条输入记录），任务块 × 机器块做笛卡尔匹配。
   热点摘要（同摘要海量行对）只会产生更多磁盘结果批次，内存驻留不增长。
3. **结果刷盘**：结果缓冲每 256 条原子写一个批次文件（临时文件 + `os.replace`），
   内存中结果永不超过 256。
4. **断点续跑**：每个 (桶, 任务块, 机器块) 单元完成并刷盘后，原子更新 `state.json`
   记录游标；进程重启后从磁盘状态恢复，跳过已确认单元。分桶阶段中断则整侧重写
   （先删旧分桶文件），join 阶段中断只重算未确认的当前单元。
5. **最终合并**：流式拼接所有批次为 `pairs.csv`，不整体载入内存。

## 调度模型（`app/app.py`）

```
上传 → 暂存目录写入+fsync → state{phase:queued} 落盘+fsync → 原子改名发布
     → 入队（新作业队列）→ 有空执行位才创建线程
启动 → 后台线程扫描 jobs 目录 → 可恢复作业入队（旧作业队列，最多占 1 个执行位）
线程结束 → 释放执行位 → 立即补位等候作业
```

- 只有运行中的作业有线程；`MAX_CONCURRENT_JOBS` 是执行位数上限。
- `state.json` 的 `phase` 同时承担"调度状态"（`queued`）和"引擎进度"
  （`partitioning` / `joining` / `done` / `failed`），重启后只看盘。

## 用 Docker Compose 启动

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

作业数据写入命名卷 `layer_matcher_data`（容器内 `/data/jobs`）。
容器/进程重启后，后台扫描会把中断作业（含"已接单未开跑"）重新入队：
先恢复一份旧作业，其余执行位留给新上传；等候作业不占线程。
`docker compose ps` 的健康检查直接探活首页，启动恢复在后台进行，不阻塞探活。

## 本地开发与自测

无需 Docker（本机无容器运行时时）：

```bash
# 安装 Flask 到独立目录（不污染系统环境）
python3 -m pip install --target=.pylibs flask==3.0.3   # 或使用已有的 get-pip

# 引擎自测（仅标准库，不需要 Flask）
python3 -I -m unittest discover -s tests -t .

# 含 Web/调度层的全部自测（19 项）
PYTHONPATH=.pylibs:app python3 -I -m unittest discover -s tests -t .

# 端到端演练（真实 Flask 进程 + 真实引擎，端口 8010）
python3 -I tests/drill_restart.py

# 命令行跑一个作业（作业目录内需有 tasks.csv / machines.csv）
PYTHONPATH=.pylibs:app python3 -I cli/run.py /path/to/job
# 故障注入：第 N 个检查点模拟写盘中断（退出码 3），再次执行即续跑
PYTHONPATH=.pylibs:app python3 -I cli/run.py /path/to/job --crash-after 1610
```

## 输入 CSV 格式

- 任务表：`任务号, 层摘要`（别名：task_id/job/task + digest/layer/sha256/hash）
- 构建机表：`来源构建机, 层摘要`（别名：machine/host/builder + digest/...）
- 空摘要行无法参与等值连接，会跳过并在作业页计数展示。

## 自测覆盖（19 项，全部通过）

- 正确性：多摘要全部行对、每对一次；空摘要跳过；无匹配产出仅表头文件
- **热点摘要**：600×600 同摘要（36 万对）+ 冷数据，注入内存守卫跑完整流程，
  断言输入记录峰值 ≤ 256、结果峰值 = 256（达上限即刷盘）
- **中断续跑**：进程内故障注入后续跑结果与一次跑完一致；
  两个独立子进程模拟真实写盘中断与重启接力；第三次执行验证幂等无重复；
  分桶阶段中断同样可恢复
- Web：上传→状态轮询→完成前下载 409、完成后 200 且列名正确；
  坏表头 400；构造 joining 中断态后调用启动恢复，已确认批次保留
- **调度**（9 项）：
  - 4 个作业并发上传时只有 2 个在跑，另 2 个排队且不在 `_threads` 中；
    页面同时出现"运行中"与"等候执行"
  - 3 个重启前作业 + 1 个新上传：旧作业只占 1 个执行位，新作业立即用另一个
  - 3 个扫描线程 + 上传 + 页面访问交错：每个作业恰好执行一次
  - 慢扫描不阻塞首页请求（后台线程）
  - `phase=queued` 作业重启后入队并跑完
  - 上传写文件失败 / 状态落盘失败：返回 5xx、目录清空、无队列条目、无线程
  - 接单前断言 `state.json` 已存在且 `phase=queued`
  - 上次崩溃留下的 `.incoming-*` 暂存目录：扫描时清理、不当作业执行、不上首页

## 端到端演练结果（`tests/drill_restart.py`，本机实测）

场景：2 个"重启前接单"的积压作业（600×600 热点摘要，36 万对/个）在盘上 →
冷启动 → 上传短作业 → 两个大作业占满执行位、第三个排队 → `SIGKILL` 重启。

| 检查项 | 实测 |
| --- | --- |
| 冷启动就绪（后台扫描中即可访问首页） | 0.21s，首页立即 200 |
| 积压作业执行名额 | 运行 1、等候 1 |
| 扫描/积压期间上传短作业 | 上传到完成 0.02s，配对 6/6，下载 7 行（表头+6） |
| 排队作业落盘状态 | `phase=queued` |
| 重启就绪 | 0.17s，首页立即 200 |
| 已接单未开跑作业 | 重启后入队完成，配对 205716（期望 205716） |
| 已开跑作业续跑 | 完成，配对 205716，下载 205716 行且全部唯一 |
| 均已完成后 | 状态保持 `done`，不被重复执行 |
| 两个积压作业 | 最终均完成，各 360000 对 |

## 已知限制 / 剩余事项

- 当前交付环境没有 Docker 守护进程（`docker` 命令不存在，且无 root/user namespace），
  `docker compose up` 只做了 compose/Dockerfile 静态校验（YAML 解析、字段核对），
  未实际构建镜像；需在有 Docker 的环境执行一次 `docker compose up --build` 冒烟。
  本轮用同一份代码以独立进程 + 独立数据目录 + 真实 HTTP 完成了等价的启动/重启演练。
- 容器内用 Flask 自带开发服务器（单进程多线程，符合"同实例调度器 + 状态文件"
  的设计）；上生产建议换 gunicorn 单 worker（多 worker 会各自调度，需加作业级
  分布式锁）。
- 调度器是**进程内**的：若同一数据卷被两个容器同时挂载，各实例会各自入队，
  同一作业可能被执行两次（引擎结果批次按单元确定性覆盖，不会产生重复行，
  但会浪费算力）。单 Compose 实例部署下不存在该问题。
- 上传大小上限 50MB（`app.py` 中 `MAX_UPLOAD_BYTES` 可调）；单次上传在内存外
  流式落盘，但 Flask 仍会先缓冲请求体。
- 停止进程时正在写的作业会停在最近确认的检查点，重启后从该点续跑；
  已写入但未推进游标的批次会在重算前被清理，不会重复计数。
